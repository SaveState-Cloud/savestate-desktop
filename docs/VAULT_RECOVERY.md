# Client-owned vault recovery

This client implements the version 1 master-key envelope served by the
SaveState API account-recovery contract. Account recovery and vault recovery
are intentionally separate operations.

## Key hierarchy

- The account master key (AMK) is 32 random bytes generated by the desktop.
  It remains the data/repository key and is never sent to the API.
- `keyId` is the first 18 bytes of
  `SHA-256("savestate-envelope-key-id-v1" || AMK)`, encoded as unpadded
  base64url. It lets a client reject an unrelated local key before use.
- The API rotation proof is unpadded base64url of
  `HMAC-SHA-256(AMK, "savestate-envelope-verifier-v1")`. The API stores only
  `SHA-256(proof)` and never returns that hash.
- Windows Credential Manager may retain the AMK when the user selects
  **Remember me**. The client accepts that AMK for an envelope only after its
  derived `keyId` matches; a password-slot rotation then also has to pass the
  API's AMK-derived proof check.

## Version 1 envelope slots

Every envelope has exactly one `password` slot and one `offline_recovery`
slot. Unknown metadata and future `trusted_device` or `webauthn_prf` slots are
preserved when the password slot rotates.

Both slots wrap the same 32-byte AMK with AES-256-GCM and a random 96-bit
nonce. Authenticated associated data binds the envelope version, `keyId`, slot
ID and type, KDF identifier, KDF parameters, and salt. A slot cannot be moved,
retagged, or have its metadata altered without authentication failing.

The password-slot KDF is a fixed, serialized profile rather than library
defaults:

- Argon2id version 0x13;
- 19,456 KiB memory;
- 2 iterations;
- parallelism 1; and
- 32 output bytes.

The offline vault recovery key is 32 random bytes displayed as unpadded
base64url. Its AES key is
`HMAC-SHA-256(recoveryKey, "savestate-offline-vault-slot-v1")`. The raw key is
shown in only the initial native response, is removed from the frontend result
after rendering, and the envelope is not committed until the user explicitly
acknowledges saving it.

## Recovery behavior

Normal legacy login first decrypts the existing
`salt:nonce:ciphertext-and-tag` wrapper with the original password. Only after
that succeeds does the client prepare an envelope and ask the user to save the
offline vault recovery key. The API's initialize-once legacy ciphertext is
never overwritten.

After an account password reset, login may restore account access while the
vault remains locked. An envelope vault can then be unlocked with its previous
vault password, offline vault recovery key, or matching remembered-device AMK.
The client reauthenticates the current account password, wraps the same AMK in
a new password slot, and sends the next optimistic envelope revision with the
AMK proof. A concurrent stale revision is rejected by the API rather than
silently rebased.

A legacy account reset before envelope migration has no server-verifiable AMK
commitment and no offline slot. If the user supplies the old vault password,
the client can decrypt and use the existing vault locally, but it does not let
the reset bearer session create an authoritative replacement envelope. Such a
vault continues to require its previous vault password on another device.

An `auth_version` 401 clears the in-memory token, email, AMK, pending state,
and repository session cache so scheduled work stops. It does **not** delete
the Credential Manager AMK. Explicit sign-out remains the operation that
removes remembered local material.

Email links, TOTP values, and one-time account recovery codes recover account
login only. UI copy must never call those values “vault recovery keys” or imply
that they decrypt existing backup contents.
